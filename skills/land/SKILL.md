Close the lifecycle for work that is ready to land: squash merge the pull request when it is still open, then reconcile the tracker and retire the task worktree.

Pull request or ticket: $ARGUMENTS

## Why

Merging publishes to the shared default branch and is hard to undo, so only a human's explicit `/land` authorizes it. That invocation is the whole approval for squash-merging the resolved open pull request and closing its lifecycle; no argument or second confirmation is added. If this skill is reached any other way, stop and tell the human to invoke `/land` from the worktree to land. Cleanup phrasing and a ready branch are not approval.

The pull request's state selects the lane (step 2). Mergeability and conformance are checked before merging; after someone else's merge, conformance can only report a mismatch and stop cleanup.

This capability merges, reconciles an authorized tracker binding, and retires a clean retained task worktree. It needs no prior delivery workflow and changes no application code. It acts only on the branch checked out where it runs, so a stack lands one `/land` per worktree, bottom up.

## Steps

1. Resolve the pull request from the current worktree. Land only the pull request whose head is the branch checked out here (`git branch --show-current`, then `gh pr view --json number,headRefName,baseRefName`). A number or ticket id in the arguments is a cross-check: resolve it, a ticket through its closing reference, and when it is not that same pull request number, stop. Name the worktree holding its branch from `git worktree list --porcelain`, or say that none does, so the human runs `/land` there; a matching branch name is not enough, because a reused branch or a fork can share it. A detached HEAD, the default branch, or a branch with no pull request stops as a finding. Read `headRefOid` and `isCrossRepository` too: a pull request from a fork stops, because its branch lives in another repository, and so does a checkout that is not that pull request's head (in the open lane `git rev-parse HEAD` must equal `headRefOid`; in the merged lane it must be `headRefOid` or an ancestor of it), since a reused branch name can resolve to an older pull request. An open pull request whose `baseRefName` is not the default branch also stops: it is stacked on a base that has not landed, so name the base's pull request to land first, since merging now would squash this branch into the base instead of the default branch. When that base is already merged, name the retarget instead (`gh pr edit <n> --base <default>`) for the human to run before `/land` again. Read closing references or linked tracker metadata; a ticket is optional.

2. Pick the lane from the state. Run `gh pr view <n> --json state,isDraft,mergedAt,headRefName`.

   `MERGED` runs the merged lane: skip to step 7. There is nothing left to merge, and steps 9 and 10 condition the remote-branch deletion and the dependents report on this run having done the merging.

   `OPEN`, not a draft, runs the open lane: steps 3 through 6, then step 7.

   A draft stops and is reported as a finding, not an error. Any state outside the lanes above also stops as a finding. Check `isDraft` because drafts also have state `OPEN`. Closed unmerged requests belong to `/abandon`.

3. Repair this branch, then gate before merging.

   Repair only a branch that still carries a base an earlier `/land` squash-merged, which happens when it was stacked on a branch that landed and was retargeted to the default branch by that run's step 6. Find the boundary from the landed pull requests, not from content alone, because content can match by accident (an empty commit, a hotfix also cherry-picked to the default branch) and can mislead when the base changed after this branch forked:

   - Fetch. Take the oldest commit in `origin/<default>..HEAD` and list the other merged pull requests it belongs to: `gh api repos/{owner}/{repo}/commits/<sha>/pulls`, keeping entries with `merged_at` set and a number other than this one, and preferring one whose `base.ref` is the default branch when several remain. With none, the branch needs no repair; go to the gate.
   - Otherwise the boundary is `git merge-base HEAD <that entry's head.sha>`. Repeat from the first commit after the boundary until that commit belongs to no other merged pull request, so a stack of several landed bases is walked one base at a time.
   - The boundary must already be on the default branch by content: `git merge-tree --write-tree origin/<default> <boundary>` prints `git rev-parse origin/<default>^{tree}` as its first line. Anything else means the base changed, was amended, or was reverted after this branch forked off it, so rebasing would keep or revive work the default branch does not have; report the branch and stop.
   - A merge commit in the range (`git rev-list --merges origin/<default>..HEAD` prints anything) is reported, not rebased, because it can hide absorbed commits under a clean-looking tip.

   Then rebase without touching the branch until every check passes. Stop when `git status --porcelain` prints anything, since a rebase would carry or stash someone's uncommitted work, and when an ignored file here (`git ls-files --others --ignored --exclude-standard`) is a path `origin/<default>` tracks (`git ls-tree -r --name-only origin/<default>`), since checking out the default branch's tree overwrites it. Record the old head and run `git rebase --no-autostash --onto origin/<default> <boundary> <old head>`, which works on a detached HEAD and leaves the branch where it was. On a conflict, run `git rebase --abort`, which leaves HEAD detached at the old head, then `git switch <branch>`, and report it. Confirm this branch's own change survived: `git diff -U0 <boundary> <old head> | git patch-id --verbatim` must be non-empty and equal `git diff -U0 origin/<default> HEAD | git patch-id --verbatim`; zero context keeps new default-branch lines near the hunks from changing the id, two empty ids compare equal, and a difference means the boundary was wrong. Run the repository's local rungs on the detached result. On any failure, `git switch <branch>` returns to the untouched branch; report what failed. Only after all of it passes, push the detached result with `git push --force-with-lease=refs/heads/<branch>:<old head> origin HEAD:refs/heads/<branch>`, which fails if the remote is not exactly the old head; on that failure `git switch <branch>` returns to the untouched branch and the run reports it. Only after the push succeeds, move the branch with `git branch -f <branch> HEAD` and `git switch <branch>`, and wait for the required checks on the new head with `gh pr checks <n> --required --watch` run in the background before the gate.

   Gate. Run `gh pr view <n> --json state,mergeable,mergeStateStatus,statusCheckRollup,reviewDecision`. Stop and report, as a finding rather than an error, on any of: a non-`MERGEABLE` mergeable state, a `DRAFT` merge state, a required check that is failing, pending, or unavailable, a missing required forge approval, or an unresolved review thread. `DRAFT` is step 2's stop reached a second way, and cheap to keep: `mergeStateStatus` knows it here without a second field. A branch behind its base needs an update only when the forge requires it. Shared history stays as it is: no rebase or force-push without authority. A red required check is never merged past.

   List and name direct dependents with `gh pr list --state open --base <headRefName> --json number,headRefName`. They do not block merging but need step 6. Record the head's current tip SHA now for step 5.

4. Verify the result against the available request, PR description, and linked ticket when present. An existing inline `## Contract` may supply requirements. Inspect relevant changes and verification evidence at the current head. A review the human requested, or that a named risk requires, must be verified before merging unless the human explicitly accepted reduced assurance; routine work needs none.

   In the open lane, check that a required review still covers the head being merged. When the review was required (the human asked for it, or the PR body's change map lists `critical` items) and the PR body has no `Reviewed: <base>..<sha>` line (written by `open-pr`), treat the review as unverified. Otherwise fetch, then confirm both `git rev-parse --verify origin/<baseRefName>^{commit}` and `git rev-parse --verify <sha>^{commit}` resolve; if either does not, the review is stale, because a base or reviewed commit that is gone cannot be compared. When `<sha>` is not an ancestor of the head, the reviewed commit may still sit on absorbed base work, whether this run or an earlier one repaired the branch: run step 3's boundary search from `<sha>` (over `origin/<default>..<sha>`), and when it finds a boundary, use `git diff <boundary> <sha>` as the reviewed side in place of every three-dot diff from `<sha>` below, both the whole-patch and the per-file comparisons. Diff both sides against the PR's current base, `origin/<baseRefName>`, rather than the base recorded in the line, so commits the base gained before a rebase never count as changes. Compare `git diff origin/<baseRefName>...<sha> | git patch-id --verbatim` with `git diff origin/<baseRefName>...<head> | git patch-id --verbatim`, where `<head>` is the tip SHA recorded in step 3; `--verbatim` keeps whitespace, which changes behavior in Python, YAML, or Makefiles. Pass `-U0` to every diff in this comparison, whole-patch and per-file, so default-branch edits near a hunk do not change an id the reviewed patch still matches. Equal, non-empty ids mean the head carries the reviewed patch and the review stands. When they differ, find the files whose own three-dot diffs differ (`git diff origin/<baseRefName>...<sha> -- <file>` against `git diff origin/<baseRefName>...<head> -- <file>` for each file either diff touches). The review still covers the head only when every such file is a test or documentation file whose changed hunks you have read and found to change no shipped behavior; a lockfile, a generated file, or any other file changed after the review makes it stale. A stale or unverified required review is a finding like a failing check: report it, and hold the merge unless the human, who invoked `/land`, accepts the reduced assurance in this session. A stale review that was never required is reported without holding the merge.

   Ask only about consequential missing requirements. A blocking mismatch stops before merging, or stops cleanup when the merge already happened. Fixes remain maintenance work on the existing branch while open; do not restart a lifecycle.

5. Squash merge, then confirm it landed. `gh pr merge <n> --squash --match-head-commit <head recorded in step 3>`, so a push after the checks above fails the merge instead of landing unchecked code. The subject is the pull request title, which is already Conventional; the body carries the resulting behavior and material assumptions from the pull request description rather than a list of the squashed commits. Omit `--delete-branch`: its post-merge local checkout fails on a repository whose default branch is checked out in another worktree, which reports an error after the merge has already succeeded and reads as a failed merge. Step 9 deletes the remote branch instead. Then re-read `gh pr view <n> --json state,mergedAt,mergeCommit`. Anything but `MERGED` stops here and is reported, including when the merge command exited non-zero for the reason above; check the state, do not assume either outcome.

6. Retarget direct dependents before deleting anything. For each dependent from step 3, run `gh pr edit <n> --base <default branch>` while the old base still exists, then read back its base. A failed retarget is reported and keeps the head branch alive in step 9. Rebase and push no other branch: each dependent still carries the commits this run squashed, and its own `/land`, run from its worktree, removes them in step 3.

7. Verify the merge and default-branch health. Fetch and prune, locate `<default>`'s worktree with `git worktree list`, then run `git -C <that path> merge --ff-only origin/<default>`. Run the repository-required local checks on the updated default branch and report failures before cleanup. Pass `-C` so the right branch is updated, and use it in place of `git checkout <default>`, which fails when another worktree owns the branch.

   When recovery material exists, read `continuity` and preserve it before retirement. Record the confirmed merge and remaining cleanup in the retained copy of the task document outside a checkout slated for retirement; mirror if available. Keep the merged checkout clean of this bookkeeping, create no checkpoint merely to land, and leave legacy records as they are.

   Reaching this step straight from step 2, run step 4's conformance check here and resume at step 8 rather than step 5, because steps 5 and 6 belong to the run that does the merging. Someone else merged this pull request, so a blocking mismatch is reported rather than prevented, and the landing stops here.

8. Reconcile the tracker only for ticket-bound work. Where `setup-harness` installed the GitHub lifecycle workflow, confirm it already ran: the ticket closed, the parent closed once every child had merge evidence, and each unblocked sibling moved to mapped `ready_for_agent`. Where it did not run, or the tracker is not GitHub, apply those transitions by hand and say which ones you applied. Where the tracker is local markdown, read the `local-tracker` skill: the transitions are file edits that must be committed and pushed on the default branch, which step 7 has already fast-forwarded past the merge, and before step 9 retires the worktree. The explicit landing request covers these scoped reconciliation writes; name and verify their files and transitions without a repeated confirmation. Preserve unrelated default-branch work. A protected branch or transition outside that authority stops only dependent cleanup. A parent closes only when every child has merge evidence. For trackerless work, skip tracker transitions.

9. Retire only this run's checkout, and only when clean. When it is a linked worktree, first list `git status --porcelain --ignored`: removal deletes ignored files too, so report each one, and refuse when any is local configuration or a secret (such as `.env*` or local settings) rather than regenerable build output, so the human can move it. Then remove it from the main checkout, the first entry of `git worktree list --porcelain` (`git -C <that path> worktree remove <this path>`), since a checkout cannot remove itself. When this run is in the main checkout itself, leave the checkout and its branch in place and report it. A squash merge leaves the local branch unmerged by ancestry, so delete it with `git -C <that path> branch -D <branch>` only after `git merge-tree --write-tree origin/<default> <branch>` prints `git rev-parse origin/<default>^{tree}` as its first line, which proves its content landed (POLICY's floor row on worktrees; only `land` and `abandon` retire a task worktree). Delete the remote head branch as well when this run did the merging, and only once step 6 retargeted every dependent; a dependent still based on it keeps it alive. If the checkout holds uncommitted changes or unpushed commits, refuse and report instead: this skill discards nothing, and `/abandon` is what discards unmerged work.

10. Report the pull request, whether this run merged it and the merge commit when it did, the requirements source, the review status (current, covered with later tests or docs, stale and accepted, or none required), the remote branch deleted, and the worktree removed. Report whether step 3 repaired this branch, with its boundary and the landed pull requests it came from. Where this run merged, report every dependent pull request it retargeted, and that each one repairs itself when `/land` runs from its own worktree. The merged lane skips steps 3 and 6, so it reports that dependents were neither enumerated nor retargeted, which is not the same as reporting none. For ticket-bound work, also report the ticket and parent states, labels moved, and next ready frontier. For trackerless work, report that tracker reconciliation was skipped.
