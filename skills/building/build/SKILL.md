Build what was asked, sized by the input. **One slice** (a plain request, one ticket, or an epic that has only one slice) is built in this session with `tdd`. **Several slices** (an epic or a set of tickets with more than one slice, however many are ready at first) are built unattended: plan one atomic pull request per slice, stacked where a slice builds on another and independent where it does not, with the blast radius deciding what may share a pull request; fan the unblocked slices out to executors, land each finished slice on its pull-request branch locally, and finish with every branch verified, mapped, and reviewed, ready for a human to read and merge one at a time.

Input: $ARGUMENTS

## Why

The several-slice path runs many workers without supervision and spends model budget at that scale, so only a human starts it: by typing `/build` or through `/jvillegasd-mode`. The invocation authorizes its branches and worker worktrees, local merges and rebases of its unpushed branches, and the floor's delivery of its pull requests; never a tracker write or a merge the floor holds back. Under jvillegasd-mode, the mode's Deciding and getting stuck rules replace this skill's asks and stops.

Atomic pull requests sized by blast radius let a human read a risky change in full and land or revert each slice on its own, where one combined pull request mixes a migration with its docs. Computing the frontier from committed work, rather than from tracker counts, keeps the run correct when a ticket is closed by hand or a label goes stale mid-run. Running one slice end to end before fanning out means a broken brief fails once instead of N times.

## One slice

1. Read the request and the relevant code; for a ticket, read its body and full comment thread. State the intended behavior and smallest change. Resolve routine details from repository conventions, and ask only about consequential gaps in scope or acceptance criteria.
2. Inspect Git state and get on the task branch as the floor's Working rules describe, in a sibling worktree when separation helps. Make the smallest complete change (`principle-laziness-protocol`). Keep a task document only when recovery across an interruption warrants one.
3. Read and use `tdd`. Reuse the seams the epic or ticket chose; otherwise pick the highest public boundary that fails for the right reason and record why. For each behavior change, watch one meaningful test fail for the intended reason, implement enough to pass, then move on. Documentation and mechanical changes use appropriate checks rather than manufactured tests. When a meaningful red test cannot be run, go on with the strongest check available and report it as that gap. When the implementation would fill this session's context (many files, a broad mechanical sweep, long generated output), write the failing tests at the seam here, hand the code that turns them green to an `executor` through `delegation`, on the model `harness models role resolve executor --json` returns (`principle-launch-on-the-assigned-model`), and review its diff rather than typing it (`principle-guard-the-context-window`).
4. Run the relevant and all repository-required checks, bound to the committed revision or the uncommitted content as `verify-work` describes. Commit owned work where authorized. Use `change-map` for a multi-file handoff and `review` when its Level section calls for one.
5. Report the behavior delivered, commits, checks, and gaps, with observed red and green results apart from unavailable checks. Then deliver it with `open-pr`, unless the human said to keep it local.

## Several slices

1. Read the epic and its slices in full, with their threads, and the agreed test seams. An epic without slices is cut into them first with `epic`'s steps 4 and 5, drafted locally, without publishing. For drafts, run `harness tickets check <feature-slug>`. Stop and ask when the seams were never agreed, a slice has no acceptance criteria that fail on the base, or the check reports a problem, such as a blocking cycle, because workers cannot repair those.
2. Plan the pull requests by blast radius before any code. Rate each slice from the paths its scope names, matched by hand against the rules `harness change-map` applies to a diff (the repository's `criticalPaths` in `docs/agents/harness.json` and the built-in critical rules), since the command classifies only files that already changed, and from whether it is a one-way door (a data migration, a deletion, a published interface). Step 6 checks the rating against the slice's real change.
   - **One pull request per slice** is the default, because each lands or reverts on its own.
   - **A slice that is `critical` or a one-way door** always gets its own pull request and shares it with nothing, so the human reads it line by line apart from the rest.
   - **Slices may share a pull request** only when every one of them is low blast radius (no `critical` path, a two-way door) and each alone is too small to review on its own, such as a `tests-docs` or `mechanical` slice beside the behavior it supports. When the whole epic is that small, one pull request is the plan.
   - **Shape the stack from the blocker graph.** A pull request whose slices have no blocker branches from the default branch, so an independent one lands on its own. One whose slices build on another pull request's slices branches from that pull request's branch and targets it, as `open-pr`'s [stacks](../../delivery/open-pr/references/stacks.md) reference describes; siblings may share a parent. When a slice's blockers sit on two pull requests, stack one of those on the other in the plan, so every slice has one parent. Where the edges allow, put the riskiest pull request lowest, so it is reviewed and lands first (`principle-sequence-verifiable-units`).
   - Create each pull-request branch when its parent is complete, named as the floor's Working rules name a task branch. Record the base SHA, and keep a task document (`checkpoint`) with each pull request's branch, parent, slices, the blast radius that decided it, and its status, plus a `## Decisions` table when the run is long.
3. Compute the frontier: the slices whose blockers are all committed on their pull request's branch or a branch below it, and whose own pull request's parent branch is complete. Use the commits on those branches as the source of truth for what is done. For drafts, run `harness tickets frontier <feature-slug> --done <committed numbers>` and take its `ready` list, holding back each slice whose pull request's parent is not complete yet, since the command does not know the plan; for published tickets, read tracker state only to find the edges.
4. Run the first slice alone, end to end: brief it, build it, check it, commit it on its branch. Fan out only after it succeeds, and revise the brief template if it failed.
5. Before launching, list each frontier slice's expected file set from its scope and a quick search of the code it names. Slices whose sets overlap never run at the same time: launch one, and start the next from its pull-request branch's tip after the first is committed there (when they belong to different pull requests, the later pull request waits on the earlier one as a blocker), because parallel edits to one file come back as conflicts the parent must resolve by hand. For each frontier slice that overlaps no running slice, launch one `executor` in its own worktree branched from the current tip of the slice's pull-request branch, on the client, model, and effort `harness models role resolve executor --json` returns (`principle-launch-on-the-assigned-model`), natively or through T3 Code's `delegate_task` with `isolation: "worktree"`, as `delegation` describes; commit that tip first, because T3 Code prepares the child's checkout from the parent's commit. Write each brief to stand alone: the goal, the scope it may touch (its file set), the exact base SHA, how to verify it, and what to report, with file pointers rather than pasted contents. Tell the executor to use `tdd` at the agreed seams and to report a short result with `path:line` pointers, not its logs. Executors never commit, push, or merge. Build a slice yourself instead when it touches concurrency, a cross-cutting interface, or a `critical` path, because those need the session's model rather than the executor's cheaper one; commit it like any other slice.
6. When an executor reports, check the result against its scope and the actual Git state in its worktree; a completion message is not evidence. A file outside the slice's set is a scope finding: keep it only when the slice needed it, no running slice owns that file, and it does not raise the slice's blast radius past what step 2 planned; otherwise move the slice to its own pull request or report it. A missing or unverifiable result is a gap, not a pass. Rerun the verification commands yourself.
7. Commit each verified slice. The parent commits it on the worker's branch with a Conventional Commit, then merges that branch into the slice's pull-request branch locally (a fast-forward when the slice is the branch's only one). Resolve a conflict by reading both sides; when it needs a product decision, record the gap and continue with independent slices. Then retire the executor worktree with `harness worktree retire <path> --into <pull-request branch>`, which removes the worktree and deletes the worker branch only when it is merged and the worktree holds no other work. When it refuses over ignored paths, pass `--allow-ignored` only when every path it lists is regenerable build output, since removal deletes them too. A slice whose merge stopped, or any other refusal, leaves the worktree in place, listed in the output. A pull request is complete when all its slices are committed; create its children's branches from its tip then. Recompute the frontier and continue from step 5 until no slice remains ready.
8. Apply the floor's stop rule per slice. When two fixes built on the same idea fail a slice's check, test that idea before another fix; when the test shows it is wrong and there is no new one, the slice stops and is reported with what was tried and the evidence, and its dependents and every pull request stacked above it wait. When a slice shows that a premise the whole epic shares is wrong (for example, the agreed seam cannot test the behavior), stop launching new slices and report it, because every remaining slice inherits the same mistake.
9. When every slice is committed, take each pull-request branch from the root up. Run `verify-work` at its own head, since each must pass the required checks without the branches above it, then `change-map` and `review` against its parent branch, as `review`'s Level section sets for a build, so each pull request has its own map and verdict. Pass the full epic and agreed seams verbatim to the general reviewer. At `off`, report the branch unreviewed. Commit a confirmed fix on the branch that owns the code, record it `fixed` with its commit, rebase the branches above it onto the new tip (they are local and unpushed, so no shared history changes), and rerun their checks. If a required correction cannot be made and rechecked, report the gap.
10. End with every branch ready. Open the pull requests with `open-pr` from the root up, each targeting its parent as the stacks reference describes, unless the human said to keep the work local. Do not merge or write to the tracker on your own. List every executor worktree step 7 left in place, with the reason.

## Output

For one slice, step 5's report. For several:

- The pull-request plan: each branch with its parent, its slices, and the blast radius that decided it.
- Slices done, each with its commit and branch, and the slices that remain.
- Gaps: missing or unverifiable results, stopped slices with their evidence and the branches waiting on them, and decisions that wait on the human.
- Checks per branch, each with its command and result against that branch's head.
- The change map and review outcome per branch, or that review was unavailable.
- The pull request links, unless the work was kept local.
