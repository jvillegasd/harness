# Stacked pull requests

A pull request is stacked when another open pull request uses its head branch as its base. Squash merging replaces the head's commits with one new commit, so each direct dependent must be retargeted and rebased off the absorbed commits before the head branch goes.

## Enumerate

`harness land check` lists the direct dependents as `dependents`. Each one's `headRefOid` is its lease, and the verdict's `head` is the boundary tip below. Repair only a dependent whose `mine` is true: another author's branch is theirs to rebase, so report it instead. After a merge, the forge may already have retargeted a dependent to the default branch; retargeting again is harmless.

## Repair

Fetch first and rebase onto `origin/<default>`; the local default branch lacks the squash until it is updated.

For each direct dependent: retarget it with `gh pr edit <n> --base <default branch>` while the old base still exists, so a failure surfaces here rather than after the deletion has already made it unrecoverable. Then drop the absorbed commits from its head with `git rebase --onto origin/<default> <boundary> <dependent head>`, where the boundary is the commit the dependent was built on. A dependent holding a merge commit (`git rev-list --merges origin/<default>..<dependent head>` prints anything) is reported, not rebased: a merge such as GitHub's "Update branch" can make the recorded tip an ancestor while the old commits still sit underneath. When the boundary tip is an ancestor of the dependent (`git merge-base --is-ancestor`), that tip is the boundary. Otherwise the head was rewritten after the dependent branched, as when an earlier `/land` in a stack rebased it onto the default branch, and the dependent still sits on the head's old commits; the recorded tip would replay those absorbed commits onto the squash and conflict. Find them with `git cherry <recorded tip> <dependent head>`, which marks `-` each commit whose patch is already on the head; the boundary candidate is the last `-` line, and with none, report the dependent. The order of those lines proves nothing: a dependent's own commit that matches a head commit (a shared cherry-pick, an empty retrigger commit) is marked `-` too, and a boundary there silently drops the dependent's earlier commits. So, in either case, verify the boundary by content: everything the dependent holds up to it must already be on the default branch, which holds when `git merge-tree --write-tree origin/<default> <boundary>` prints `git rev-parse origin/<default>^{tree}` as its first line. Anything else means the boundary still carries the dependent's own work, or work the squash dropped; report the dependent instead of rebasing. Before pushing, confirm the dependent's own change survived: `git diff <boundary> <its recorded lease> | git patch-id --verbatim` must be non-empty and equal `git diff origin/<default> <rebased dependent> | git patch-id --verbatim`. An empty id is a failure, since two empty ids compare equal. A difference means a wrong boundary or new default-branch work beside the dependent's hunks; read the differing files, and report the dependent unless the default branch's new commits explain every difference. Run that branch's own local rungs, and push with `git push --force-with-lease=refs/heads/<dependent head>:<its recorded lease> origin <dependent head>`. The explicit lease fails if the dependent's owner pushed since you recorded its lease, even when a background fetch has moved the remote-tracking ref; report that dependent instead of retrying. Do the rebase in the worktree that holds the dependent's branch, where one does. Where none does, rebase in a temporary detached worktree outside every checkout, created with `git -c core.hooksPath=/dev/null worktree add --detach <path> <its recorded lease>`: run the rebase with the lease SHA in place of `<dependent head>`, push with `git push --force-with-lease=refs/heads/<dependent head>:<its recorded lease> origin HEAD:refs/heads/<dependent head>`, and remove it with `git worktree remove <path>` once the push succeeded or was reported, since it holds nothing but that rebase. A local branch of the dependent's name that no worktree holds is stale after the push: report it and leave it.

Repair only direct dependents. A deeper chain keeps sitting on the old commits until its own base lands, and that run finds its boundary as above, so rebasing it now would only repeat work. A conflict that is more than mechanical stops here: leave the head branch undeleted, report which dependents were repaired and which were not, and treat the rest as `/address-review` work.
