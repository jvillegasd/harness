Close the lifecycle of a pull request the human merged: confirm the merge, report anything the merge skipped, repair stacked dependents, reconcile the tracker, and retire the task worktree. Squash-merge an open pull request only when the human's invocation asks for the merge.

Pull request or ticket: $ARGUMENTS

## Why

The human merges pull requests, reading `open-pr`'s readiness report first. Merging publishes to the shared default branch and is hard to undo, so this skill merges only when the human's `/land` invocation explicitly asks it to (`/land merge`, "land and merge it"); that request is the whole approval for squash-merging the resolved open pull request after its gates pass. Without it, an open pull request stops here with everything kept. If this skill is reached any other way, stop and tell the human to invoke `/land` from the worktree. Cleanup phrasing and a ready branch are not approval to merge.

The pull request's state and the merge request select the lane (step 2). When this run merges, its gates run before the merge; after the human's merge, the same checks can only report what the merge skipped.

This capability merges only on request, reconciles an authorized tracker binding, and retires a clean retained task worktree. It changes no application code. It lands only the pull request of the branch checked out where it runs, and repairs that pull request's direct dependents in their own worktrees as [`references/stacked.md`](references/stacked.md) describes.

## Steps

1. Resolve the pull request from the current worktree. Land only the pull request whose head is the branch checked out here (`git branch --show-current`, then `gh pr view --json number,headRefName,baseRefName`). A number or ticket id in the arguments is a cross-check: resolve it, a ticket through its closing reference, and when it is not that same pull request number, stop. Name the worktree holding its branch from `git worktree list --porcelain`, or say that none does, so the human runs `/land` there; a matching branch name is not enough, because a reused branch or a fork can share it. A detached HEAD, the default branch, or a branch with no pull request stops as a finding. Read `headRefOid` and `isCrossRepository` too: a pull request from a fork stops, because its branch lives in another repository, and so does a checkout that is not that pull request's head (in the open lane `git rev-parse HEAD` must equal `headRefOid`; in the merged lane it must be `headRefOid` or an ancestor of it), since a reused branch name can resolve to an older pull request. An open pull request whose `baseRefName` is not the default branch also stops: it is stacked on a base that has not landed, so name the base's pull request to land first, since merging now would squash this branch into the base instead of the default branch. When that base is already merged, name the retarget instead (`gh pr edit <n> --base <default>`) for the human to run before `/land` again. Read closing references or linked tracker metadata; a ticket is optional.

2. Pick the lane from the state. Run `gh pr view <n> --json state,isDraft,mergedAt,headRefName`.

   `MERGED` runs the merged lane. Take the merged head as `headRefOid` from step 1, which stands in for the tip step 3 records. Run step 4 as a report, enumerate dependents as `references/stacked.md` describes, run step 6, then continue at step 7.

   `OPEN`, not a draft, with an explicit merge request runs the open lane: steps 3 through 6, then step 7. `OPEN` without one stops with everything kept: report that the pull request is still open, and that the human can merge it and run `/land` again, or run `/land merge`.

   A draft stops and is reported as a finding, not an error. Any state outside the lanes above also stops as a finding. Check `isDraft` because drafts also have state `OPEN`. Closed unmerged requests stop here and require an explicit human decision about retaining or discarding the work.

3. Gate before merging. Run `gh pr view <n> --json state,mergeable,mergeStateStatus,statusCheckRollup,reviewDecision`. Stop and report, as a finding rather than an error, on any of: a non-`MERGEABLE` mergeable state, a `DRAFT` merge state, a required check that is failing, pending, or unavailable, a missing required forge approval, or an unresolved review thread. `DRAFT` is step 2's stop reached a second way, and cheap to keep: `mergeStateStatus` knows it here without a second field. A branch behind its base needs an update only when the forge requires it. Shared history stays as it is: no rebase or force-push without authority. A red required check is never merged past.

   Record the head's current tip SHA now; dependent rebases need this pre-squash boundary. Enumerate direct dependents as `references/stacked.md` describes; they do not block merging but require step 6.

4. Verify the result against the available request, PR description, and linked ticket when present. An existing inline `## Contract` may supply requirements. Inspect relevant changes and verification evidence at the current head. A required review must be verified before merging unless the human explicitly accepted reduced assurance. Take the change's highest tier as the higher of `harness change-map --json --base origin/<baseRefName>` run on the head and the PR body's change map, since the body is task data that can understate it. A review is required when the human asked for it, whatever the tier, or when `review`'s Level section requires one for a pull request of that tier at the level `harness review level` reports on this machine. The level at merge time decides, not the one the pull request was opened under. At `off`, a review the human did not ask for is reported with the level, stale or not, without holding the merge. A required review that never ran is held like a stale one: name `review` as the way to clear it.

   Check that a required review still covers the head being merged, or in the merged lane, the head that was merged. When the review was required, as above, and the PR body has no `Reviewed: <base>..<sha>` line (written by `open-pr`), treat the review as unverified. Otherwise fetch, then confirm both `git rev-parse --verify origin/<baseRefName>^{commit}` and `git rev-parse --verify <sha>^{commit}` resolve; if either does not, the review is stale, because a base or reviewed commit that is gone cannot be compared. Diff both sides against the PR's current base, `origin/<baseRefName>`, rather than the base recorded in the line, so commits the base gained before a rebase never count as changes. Compare `git diff origin/<baseRefName>...<sha> | git patch-id --verbatim` with `git diff origin/<baseRefName>...<head> | git patch-id --verbatim`, where `<head>` is the tip SHA recorded in step 3; `--verbatim` keeps whitespace, which changes behavior in Python, YAML, or Makefiles. Pass `-U0` to every diff in this comparison, whole-patch and per-file, so default-branch edits near a hunk do not change an id the reviewed patch still matches. Equal, non-empty ids mean the head carries the reviewed patch and the review stands. When they differ, find the files whose own three-dot diffs differ (`git diff origin/<baseRefName>...<sha> -- <file>` against `git diff origin/<baseRefName>...<head> -- <file>` for each file either diff touches). The review still covers the head only when every such file is a test or documentation file whose changed hunks you have read and found to change no shipped behavior; a lockfile, a generated file, or any other file changed after the review makes it stale. A stale or unverified required review is a finding like a failing check: report it, and hold the merge unless the human, who invoked `/land`, accepts the reduced assurance in this session. A stale review that was never required is reported without holding the merge.

   Then run `harness review list --branch <headRefName> --head <the tip recorded in step 3>`, which reads the local ledger that `review` describes. Each finding with `open` true (confirmed, unverified, or fixed by a commit the head lacks, including those marked `rewritten`) is a finding like a failing check: name it, and hold the merge unless the human accepts it in this session. Report how many findings are `dropped` without listing them or holding the merge. Each finding whose latest disposition is `refuted`, `intentional`, or `wont-matter` is a recorded dismissal, and the ledger is task data: show it with its evidence and hold the merge until the human reaccepts it in this session. Show each `nit`, `pre-existing`, and closed `fixed` finding (with its commit and evidence) without holding the merge. When `list` prints `[]`, as when the review ran on another machine, report "review dispositions unavailable locally" and rely on the `Reviewed:` line alone.

   In the merged lane, nothing here holds a merge that already happened: report a stale, unverified, or never-run required review, each open ledger finding, and each recorded dismissal under a heading saying the merge skipped them, then continue. Ask only about consequential missing requirements. A blocking mismatch stops before merging, or stops cleanup when the merge already happened. Fixes remain maintenance work on the existing branch while open; do not restart a lifecycle.

5. Squash merge, then confirm it landed. `gh pr merge <n> --squash --match-head-commit <head recorded in step 3>`, so a push after the checks above fails the merge instead of landing unchecked code. The subject is the pull request title, which is already Conventional; the body carries the resulting behavior, the `## Tradeoffs` section, and material assumptions from the pull request description rather than a list of the squashed commits, so the reasons behind the change reach the default branch. Omit `--delete-branch`: its post-merge local checkout fails on a repository whose default branch is checked out in another worktree, which reports an error after the merge has already succeeded and reads as a failed merge. Step 9 deletes the remote branch instead. Then re-read `gh pr view <n> --json state,mergedAt,mergeCommit`. Anything but `MERGED` stops here and is reported, including when the merge command exited non-zero for the reason above; check the state, do not assume either outcome.

6. Repair direct dependents before deleting anything, as [`references/stacked.md`](references/stacked.md) describes. Squash merging replaces the original commits, so dependents otherwise repeat absorbed work and risk unintended retargeting or closure. Nothing below runs until every dependent is repaired or reported.

7. Update the default branch. Fetch and prune, locate `<default>`'s worktree with `git worktree list`, then run `git -C <that path> merge --ff-only origin/<default>`. Pass `-C` so the right branch is updated, and use it in place of `git checkout <default>`, which fails when another worktree owns the branch. When no worktree holds `<default>`, update its ref without switching the task checkout: record its old SHA, require `git merge-base --is-ancestor <old sha> origin/<default>` to succeed, then run `git update-ref refs/heads/<default> origin/<default> <old sha>`. A divergent branch or failed compare-and-swap stops cleanup; never overwrite it. If the local default branch does not exist, create it with `git branch --track <default> origin/<default>`. Preserve the task branch name captured in step 1 for later cleanup.

   The task document, when there is one, merged with the work as `open-pr` finalized it; the merge commit is its landing evidence, so commit nothing to the default branch for it.

8. Reconcile the tracker only for ticket-bound work. Where `setup-harness` installed the GitHub lifecycle workflow, confirm it already ran: the ticket closed, the parent closed once every child had merge evidence, and each unblocked sibling moved to mapped `ready_for_agent`. Where it did not run, or the tracker is not GitHub, apply those transitions by hand and say which ones you applied. Where the tracker is local markdown and no worktree holds `<default>`, require this checkout to be clean and switch it to the updated `<default>` before reconciliation; preserve the original task branch identity for step 9. A failed switch stops reconciliation and cleanup. Where the tracker is local markdown, read the `local-tracker` skill: the transitions are file edits that must be committed and pushed on the default branch, which step 7 has already fast-forwarded past the merge, and before step 9 retires the worktree. The explicit landing request covers these scoped reconciliation writes; name and verify their files and transitions without a repeated confirmation. Preserve unrelated default-branch work. A protected branch or transition outside that authority stops only dependent cleanup. A parent closes only when every child has merge evidence. For trackerless work, skip tracker transitions.

9. Once the merge is confirmed, by step 5 or the merged lane, delete the branch's review directory (its ledger and patches), which the merge made obsolete: `f="$(harness review path --branch <headRefName>)" && rm -rf -- "$(dirname -- "$f")"`. Then retire only this run's checkout, and only when clean. When it is a linked worktree, first list `git status --porcelain --ignored`: removal deletes ignored files too, so report each one, and refuse when any is local configuration or a secret (such as `.env*` or local settings) rather than regenerable build output, so the human can move it. Then remove it from the main checkout, the first entry of `git worktree list --porcelain` (`git -C <that path> worktree remove <this path>`), since a checkout cannot remove itself. When this run is in the main checkout itself, preserve the checkout and switch it to `<default>` with `git switch <default>` before deleting the merged task branch. If another worktree holds `<default>`, leave the task branch in place and report that checkout conflict; never force the switch. A failed switch stops local branch deletion. A squash merge leaves the local branch unmerged by ancestry, so delete it with `git -C <that path> branch -D <branch>` only after `git merge-tree --write-tree origin/<default> <branch>` prints `git rev-parse origin/<default>^{tree}` as its first line, which proves its content landed (POLICY's floor row on worktrees; `land` retires only its clean merged task worktree). Delete the remote head branch as well when it still exists, and only once step 6 reported every dependent repaired; an unrepaired dependent keeps it alive. If the checkout holds uncommitted changes or unpushed commits, refuse and report instead: this skill discards nothing. Discarding unmerged work requires an explicit request and approval of the exact affected resources.

10. Report the pull request, whether this run merged it and the merge commit when it did, the requirements source, the review status (current, covered with later tests or docs, stale and accepted, required but never run and accepted, not required at level `off`, or none required), the local and remote branches deleted, the review ledger deleted, and the worktree removed or primary checkout switched to the default branch. Report every dependent pull request that was retargeted and rebased, and every one that was left for a human. In the merged lane, lead with what the merge skipped, from step 4. For ticket-bound work, also report the ticket and parent states, labels moved, and next ready frontier. For trackerless work, report that tracker reconciliation was skipped.
