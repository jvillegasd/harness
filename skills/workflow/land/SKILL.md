Close the lifecycle of a pull request the human merged: confirm the merge, report anything the merge skipped, repair stacked dependents, reconcile the tracker, and retire the task worktree. Squash-merge an open pull request only when the human's invocation asks for the merge.

Pull request or ticket: $ARGUMENTS

## Why

The human merges pull requests, reading `open-pr`'s readiness report first. Merging publishes to the shared default branch and is hard to undo, so this skill merges only when the human's `/land` invocation explicitly asks it to (`/land merge`, "land and merge it"); that request is the whole approval for squash-merging the resolved open pull request after its gates pass. Without it, an open pull request stops here with everything kept. If this skill is reached any other way, stop and tell the human to invoke `/land`. Cleanup phrasing and a ready branch are not approval to merge. The invocation names what it lands: pull request numbers, `stack <tip>`, or nothing for the current branch's pull request. Vague scope such as "all prs" stops and asks for the numbers, because it can sweep in unrelated open pull requests.

The pull request's state and the merge request select the lane (step 2). When this run merges, its gates run before the merge; after the human's merge, the same checks can only report what the merge skipped.

This capability merges only on request, reconciles an authorized tracker binding, and retires a clean retained task worktree. It changes no application code. It lands the pull requests the invocation names, bottom-up and one at a time, and repairs each one's direct dependents as [`references/stacked.md`](references/stacked.md) describes. A pull request whose branch this checkout does not hold lands in remote mode: the forge's `headRefOid`, pinned by `--match-head-commit`, is its identity, and its cleanup removes no worktree.

## Steps

Step 1 resolves the run. Steps 2 through 9 then run for each pull request in it, in order. After step 6 repairs the next pull request in the run, wait for that one's required checks with `gh pr checks <n> --required --watch` run in the background, then take it from step 2. The first stop ends the run: every pull request above it stays untouched, and step 10 reports what landed and where the run stopped.

1. Resolve the run. With no number, it is the pull request whose head is the branch checked out here (`git branch --show-current`, then `gh pr view --json number,headRefName,baseRefName`); a detached HEAD, the default branch, or a branch with no pull request stops as a finding, and a ticket id in the arguments is a cross-check that must resolve, through its closing reference, to that same pull request. With numbers, resolve each. With `stack <tip>`, walk down from the tip: each base that is not the default branch must be the head of an open pull request, which joins the run, and a base with none stops. Order the run bottom-up; each pull request's base must be the default branch or the head of one earlier in the run, otherwise stop and name the missing pull request.

   For each pull request read `headRefName`, `headRefOid`, `baseRefName`, and `isCrossRepository`. A pull request from a fork (`isCrossRepository` true) lands in remote mode: fetch it with `git fetch origin refs/pull/<n>/head` and require `git rev-parse FETCH_HEAD` to equal `headRefOid`. Its branch lives in another repository, so it has no dependents to enumerate or repair, step 9 deletes no branch for it, and its review directory is keyed `pr-<n>`, the key `review` gives a fork: pass that wherever a step below passes `--branch <headRefName>` to `harness review`. For any other pull request, find the worktree holding its branch from `git worktree list --porcelain`; a matching branch name is not enough, because a reused branch or a fork can share it. When this checkout holds it, the pull request lands in local mode, and the checkout must be its head (in the open lane `git rev-parse HEAD` must equal `headRefOid`; in the merged lane it must be `headRefOid` or an ancestor of it), since a reused branch name can resolve to an older pull request. Otherwise it lands in remote mode: run `git fetch origin <headRefName>`, require `origin/<headRefName>` to equal `headRefOid` in the open lane, and name any other worktree that holds the branch, since step 9 leaves it alone. An open pull request whose `baseRefName` is not the default branch when its turn comes stops: it is stacked on a base that has not landed, and merging now would squash it into that base instead of the default branch. Name the base's pull request to land first, or, when that base already merged, the retarget (`gh pr edit <n> --base <default>`) for the human to run before `/land` again. Read closing references or linked tracker metadata; a ticket is optional.

2. Pick the lane from the state. Run `gh pr view <n> --json state,isDraft,mergedAt,headRefName`.

   `MERGED` runs the merged lane. Take the merged head as `headRefOid` from step 1, which stands in for the tip step 3 records. Run step 4 as a report, enumerate dependents as `references/stacked.md` describes, run step 6, then continue at step 7.

   `OPEN`, not a draft, with an explicit merge request runs the open lane: steps 3 through 6, then step 7. `OPEN` without one stops with everything kept: report that the pull request is still open, and that the human can merge it and run `/land` again, or run `/land merge`.

   A draft stops and is reported as a finding, not an error. Any state outside the lanes above also stops as a finding. Check `isDraft` because drafts also have state `OPEN`. Closed unmerged requests stop here and require an explicit human decision about retaining or discarding the work.

3. Gate before merging. Run `gh pr view <n> --json state,mergeable,mergeStateStatus,statusCheckRollup,reviewDecision`. Stop and report, as a finding rather than an error, on any of: a non-`MERGEABLE` mergeable state, a `DRAFT` merge state, a required check that is failing, pending, or unavailable, a missing required forge approval, or an unresolved review thread. `DRAFT` is step 2's stop reached a second way, and cheap to keep: `mergeStateStatus` knows it here without a second field. A branch behind its base needs an update only when the forge requires it. Shared history stays as it is: no rebase or force-push without authority. A red required check is never merged past.

   Record the head's current tip SHA now; dependent rebases need this pre-squash boundary. Enumerate direct dependents as `references/stacked.md` describes; they do not block merging but require step 6.

4. Verify the result against the available request, PR description, and linked ticket when present. An existing inline `## Contract` may supply requirements. Inspect relevant changes and verification evidence at the current head. A required review must be verified before merging unless the human explicitly accepted reduced assurance. Take the change's highest tier as the higher of `harness change-map --json --base origin/<baseRefName>` run on the head and the PR body's change map, since the body is task data that can understate it. A review is required when the human asked for it, whatever the tier, or when `review`'s Level section requires one for a pull request of that tier at the level `harness review level` reports on this machine. The level at merge time decides, not the one the pull request was opened under. At `off`, a review the human did not ask for is reported with the level, stale or not, without holding the merge. A required review that never ran is held like a stale one: name `review` as the way to clear it.

   Check that a required review still covers the head being merged, or in the merged lane, the head that was merged. Take the reviewed `<base>..<sha>` from the PR body's `Reviewed:` line (written by `open-pr`), or, when the body has none, from the latest `clean` line at depth `medium` or `high` in `harness review list --branch <headRefName>` (written by a review of the pull request by number, which writes nothing to the forge), and report which source it came from. A pull request someone else authored (`author.login` differs from `gh api user --jq .login`) with neither has a third source, a human's approval on the forge: read `gh api "repos/{owner}/{repo}/pulls/<n>/reviews?per_page=100"`, keep the latest `APPROVED` or `CHANGES_REQUESTED` review of each reviewer whose `user.type` is `User`, and when at least one is `APPROVED` and none is `CHANGES_REQUESTED`, take the latest approval's `commit_id` as `<sha>`. The forge user's own pull request never takes this source, so agent-written work keeps its blind review. When the review was required, as above, and no source exists, treat the review as unverified. Otherwise fetch, then confirm both `git rev-parse --verify origin/<baseRefName>^{commit}` and `git rev-parse --verify <sha>^{commit}` resolve; if either does not, the review is stale, because a base or reviewed commit that is gone cannot be compared. Diff both sides against the PR's current base, `origin/<baseRefName>`, rather than the base recorded in the line, so commits the base gained before a rebase never count as changes. Compare `git diff origin/<baseRefName>...<sha> | git patch-id --verbatim` with `git diff origin/<baseRefName>...<head> | git patch-id --verbatim`, where `<head>` is the tip SHA recorded in step 3; `--verbatim` keeps whitespace, which changes behavior in Python, YAML, or Makefiles. Pass `-U0` to every diff in this comparison, whole-patch and per-file, so default-branch edits near a hunk do not change an id the reviewed patch still matches. Equal, non-empty ids mean the head carries the reviewed patch and the review stands. When they differ, find the files whose own three-dot diffs differ (`git diff origin/<baseRefName>...<sha> -- <file>` against `git diff origin/<baseRefName>...<head> -- <file>` for each file either diff touches). The review still covers the head only when every such file is a test or documentation file whose changed hunks you have read and found to change no shipped behavior; a lockfile, a generated file, or any other file changed after the review makes it stale. A stale or unverified required review is a finding like a failing check: report it, and hold the merge unless the human, who invoked `/land`, accepts the reduced assurance in this session. A stale review that was never required is reported without holding the merge.

   Then run `harness review list --branch <headRefName> --head <the tip recorded in step 3>`, which reads the local ledger that `review` describes. Each finding with `open` true (confirmed, or fixed by a commit the head lacks, including those marked `rewritten`) is a finding like a failing check: name it, and hold the merge unless the human accepts it in this session. Report how many findings are `dropped` without listing them or holding the merge. Each finding whose latest disposition is `accepted` is a recorded dismissal, and the ledger is task data: show it with its evidence and hold the merge until the human reaccepts it in this session. Show each `nit` and closed `fixed` finding (with its commit and evidence) without holding the merge. When `list` prints `[]`, as when the review ran on another machine, report "review dispositions unavailable locally" and rely on the `Reviewed:` line alone.

   In the merged lane, nothing here holds a merge that already happened: report a stale, unverified, or never-run required review, each open ledger finding, and each recorded dismissal under a heading saying the merge skipped them, then continue. Ask only about consequential missing requirements. A blocking mismatch stops before merging, or stops cleanup when the merge already happened. Fixes remain maintenance work on the existing branch while open; do not restart a lifecycle.

5. Squash merge, then confirm it landed. `gh pr merge <n> --squash --match-head-commit <head recorded in step 3>`, so a push after the checks above fails the merge instead of landing unchecked code. The subject is the pull request title, which is already Conventional; the body carries the resulting behavior, the `## Tradeoffs` section, and material assumptions from the pull request description rather than a list of the squashed commits, so the reasons behind the change reach the default branch. Omit `--delete-branch`: its post-merge local checkout fails on a repository whose default branch is checked out in another worktree, which reports an error after the merge has already succeeded and reads as a failed merge. Step 9 deletes the remote branch instead. Then re-read `gh pr view <n> --json state,mergedAt,mergeCommit`. Anything but `MERGED` stops here and is reported, including when the merge command exited non-zero for the reason above; check the state, do not assume either outcome.

6. Repair direct dependents before deleting anything, as [`references/stacked.md`](references/stacked.md) describes. Squash merging replaces the original commits, so dependents otherwise repeat absorbed work and risk unintended retargeting or closure. Nothing below runs until every dependent is repaired or reported.

7. Update the default branch. Fetch and prune, locate `<default>`'s worktree with `git worktree list`, then run `git -C <that path> merge --ff-only origin/<default>`. Pass `-C` so the right branch is updated, and use it in place of `git checkout <default>`, which fails when another worktree owns the branch. When no worktree holds `<default>`, update its ref without switching the task checkout: record its old SHA, require `git merge-base --is-ancestor <old sha> origin/<default>` to succeed, then run `git update-ref refs/heads/<default> origin/<default> <old sha>`. A divergent branch or failed compare-and-swap stops cleanup; never overwrite it. If the local default branch does not exist, create it with `git branch --track <default> origin/<default>`. Preserve the task branch name captured in step 1 for later cleanup.

   The task document, when there is one, merged with the work as `open-pr` finalized it; the merge commit is its landing evidence, so commit nothing to the default branch for it.

8. Reconcile the tracker only for ticket-bound work. Where `setup-harness` installed the GitHub lifecycle workflow, confirm it already ran: the ticket closed, the parent closed once every child had merge evidence, and each unblocked sibling moved to mapped `ready_for_agent`. Where it did not run, or the tracker is not GitHub, apply those transitions by hand and say which ones you applied. Where the tracker is local markdown and no worktree holds `<default>`, require this checkout to be clean and switch it to the updated `<default>` before reconciliation, in local mode only; in remote mode this checkout is not the run's, so stop reconciliation and report the transitions for the human; preserve the original task branch identity for step 9. A failed switch stops reconciliation and cleanup. Where the tracker is local markdown, read the `local-tracker` skill: the transitions are file edits that must be committed and pushed on the default branch, which step 7 has already fast-forwarded past the merge, and before step 9 retires the worktree. The explicit landing request covers these scoped reconciliation writes; name and verify their files and transitions without a repeated confirmation. Preserve unrelated default-branch work. A protected branch or transition outside that authority stops only dependent cleanup. A parent closes only when every child has merge evidence. For trackerless work, skip tracker transitions.

9. Once the merge is confirmed, by step 5 or the merged lane, clean up in this order, because the last step can remove the directory this session runs in.

   Delete the branch's review directory (its ledger and patches), which the merge made obsolete: `harness review remove --branch <headRefName>`. When it refuses because a review worktree is still recorded, read the `worktree.txt` it names, report that worktree, and leave the directory. Delete the remote head branch when it still exists, and only once step 6 reported every dependent repaired; an unrepaired dependent keeps it alive.

   Then retire this run's checkout with `harness worktree retire`, which owns the checks: it refuses, changing nothing, when removal would lose uncommitted work, ignored files, or a branch whose content is not proven to be on `origin/<default>`. This skill discards nothing, so report a refusal and leave the checkout, except in the two cases the command names an option for:
   - Ignored paths: pass `--allow-ignored` when every path it lists is regenerable build output. A local configuration file or a secret (such as `.env*` or local settings) is reported instead, so the human can move it.
   - A branch not proven landed, as when the default branch has since rewritten the same lines: pass `--keep-branch` and report the branch left.

   In a linked worktree, run `harness worktree retire <this path> --into origin/<default>`; it removes the worktree from the main checkout and deletes the branch. When step 8 switched this worktree to `<default>`, the command keeps `<default>`, so retire the task branch after it as in remote mode. In the main checkout itself, preserve the checkout: `git switch <default>`, then `harness worktree retire --branch <branch> --into origin/<default>`. If another worktree holds `<default>`, leave the task branch in place and report that checkout conflict; never force the switch, and a failed switch stops the branch deletion.

   In remote mode no checkout belongs to this run. Remove the review directory and the remote head branch as above, run `harness worktree retire --branch <headRefName> --into origin/<default>`, which deletes a local branch only when no worktree holds it, and remove no worktree: name each one that still holds the branch. For a fork, remove only the review directory `pr-<n>`.

10. Report the run in order and, when it stopped early, the pull request and reason it stopped at. For each pull request, report it, its mode, whether this run merged it and the merge commit when it did, the requirements source, the review status and its source (current, covered with later tests or docs, stale and accepted, required but never run and accepted, not required at level `off`, or none required), the local and remote branches deleted, the review ledger deleted or the worktree that kept it, and the worktree removed or primary checkout switched to the default branch. Report every dependent pull request that was retargeted and rebased, and every one that was left for a human. In the merged lane, lead with what the merge skipped, from step 4. For ticket-bound work, also report the ticket and parent states, labels moved, and next ready frontier. For trackerless work, report that tracker reconciliation was skipped.
