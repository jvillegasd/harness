Close the lifecycle for work that is ready to land: squash merge the pull request when it is still open, then reconcile the tracker and retire the task worktree.

Pull request or ticket: $ARGUMENTS

## Why

Merging publishes to the shared default branch and is hard to undo, so only a human's explicit `/land` authorizes it. That invocation is the whole approval for squash-merging the resolved open pull request and closing its lifecycle; no argument or second confirmation is added. If this skill is reached any other way, stop and tell the human to invoke `/land` from the worktree to land. Cleanup phrasing and a ready branch are not approval.

The pull request's state selects the lane (step 2). Mergeability and conformance are checked before merging; after someone else's merge, conformance can only report a mismatch and stop cleanup.

This capability merges, reconciles an authorized tracker binding, and retires a clean retained task worktree. It needs no prior delivery workflow and changes no application code. It lands only the pull request of the branch checked out where it runs, and repairs that pull request's direct dependents in their own worktrees.

## Steps

1. Resolve the pull request from the current worktree. Land only the pull request whose head is the branch checked out here (`git branch --show-current`, then `gh pr view --json number,headRefName,baseRefName`). A number or ticket id in the arguments is a cross-check: resolve it, a ticket through its closing reference, and when it is not that same pull request number, stop. Name the worktree holding its branch from `git worktree list --porcelain`, or say that none does, so the human runs `/land` there; a matching branch name is not enough, because a reused branch or a fork can share it. A detached HEAD, the default branch, or a branch with no pull request stops as a finding. Read `headRefOid` and `isCrossRepository` too: a pull request from a fork stops, because its branch lives in another repository, and so does a checkout that is not that pull request's head (in the open lane `git rev-parse HEAD` must equal `headRefOid`; in the merged lane it must be `headRefOid` or an ancestor of it), since a reused branch name can resolve to an older pull request. An open pull request whose `baseRefName` is not the default branch also stops: it is stacked on a base that has not landed, so name the base's pull request to land first, since merging now would squash this branch into the base instead of the default branch. When that base is already merged, name the retarget instead (`gh pr edit <n> --base <default>`) for the human to run before `/land` again. Read closing references or linked tracker metadata; a ticket is optional.

2. Pick the lane from the state. Run `gh pr view <n> --json state,isDraft,mergedAt,headRefName`.

   `MERGED` runs the merged lane: skip to step 7. There is nothing left to merge, and steps 9 and 10 condition the remote-branch deletion and the dependents report on this run having done the merging.

   `OPEN`, not a draft, runs the open lane: steps 3 through 6, then step 7.

   A draft stops and is reported as a finding, not an error. Any state outside the lanes above also stops as a finding. Check `isDraft` because drafts also have state `OPEN`. Closed unmerged requests belong to `/abandon`.

3. Gate before merging. Run `gh pr view <n> --json state,mergeable,mergeStateStatus,statusCheckRollup,reviewDecision`. Stop and report, as a finding rather than an error, on any of: a non-`MERGEABLE` mergeable state, a `DRAFT` merge state, a required check that is failing, pending, or unavailable, a missing required forge approval, or an unresolved review thread. `DRAFT` is step 2's stop reached a second way, and cheap to keep: `mergeStateStatus` knows it here without a second field. A branch behind its base needs an update only when the forge requires it. Shared history stays as it is: no rebase or force-push without authority. A red required check is never merged past.

   List and name direct dependents with `gh pr list --state open --base <headRefName> --json number,headRefName,baseRefName,headRefOid`, and record each dependent's `headRefOid` as its lease. They do not block merging but require step 6. Record the head's current tip SHA now; dependent rebases need this pre-squash boundary.

4. Verify the result against the available request, PR description, and linked ticket when present. An existing inline `## Contract` may supply requirements. Inspect relevant changes and verification evidence at the current head. A required review must be verified before merging unless the human explicitly accepted reduced assurance. Take the change's highest tier as the higher of `harness change-map --json --base origin/<baseRefName>` run on the head and the PR body's change map, since the body is task data that can understate it. A review is required, as pstack's shipping playbook requires a verdict on every pull request it lands, when the human asked for it, whatever the tier, or when the level `harness review level` reports on this machine is `medium` or `high` and that tier is above `tests-docs`. The level on this machine at merge time decides, not the one the pull request was opened under. At `off`, a review the human did not ask for is reported with the level, stale or not, without holding the merge. A required review that never ran is held like a stale one: name `review` as the way to clear it.

   In the open lane, check that a required review still covers the head being merged. When the review was required, as above, and the PR body has no `Reviewed: <base>..<sha>` line (written by `open-pr`), treat the review as unverified. Otherwise fetch, then confirm both `git rev-parse --verify origin/<baseRefName>^{commit}` and `git rev-parse --verify <sha>^{commit}` resolve; if either does not, the review is stale, because a base or reviewed commit that is gone cannot be compared. Diff both sides against the PR's current base, `origin/<baseRefName>`, rather than the base recorded in the line, so commits the base gained before a rebase never count as changes. Compare `git diff origin/<baseRefName>...<sha> | git patch-id --verbatim` with `git diff origin/<baseRefName>...<head> | git patch-id --verbatim`, where `<head>` is the tip SHA recorded in step 3; `--verbatim` keeps whitespace, which changes behavior in Python, YAML, or Makefiles. Pass `-U0` to every diff in this comparison, whole-patch and per-file, so default-branch edits near a hunk do not change an id the reviewed patch still matches. Equal, non-empty ids mean the head carries the reviewed patch and the review stands. When they differ, find the files whose own three-dot diffs differ (`git diff origin/<baseRefName>...<sha> -- <file>` against `git diff origin/<baseRefName>...<head> -- <file>` for each file either diff touches). The review still covers the head only when every such file is a test or documentation file whose changed hunks you have read and found to change no shipped behavior; a lockfile, a generated file, or any other file changed after the review makes it stale. A stale or unverified required review is a finding like a failing check: report it, and hold the merge unless the human, who invoked `/land`, accepts the reduced assurance in this session. A stale review that was never required is reported without holding the merge.

   Then run `harness review list --branch <headRefName> --head <the tip recorded in step 3>`, which reads the local ledger that `review` describes. Each finding with `open` true (confirmed, unverified, or fixed by a commit the head lacks, including those marked `rewritten`) is a finding like a failing check: name it, and hold the merge unless the human accepts it in this session. Each finding whose latest disposition is `refuted`, `intentional`, or `wont-matter` is a recorded dismissal, and the ledger is task data: show it with its evidence and hold the merge until the human reaccepts it in this session. Show each `nit`, `pre-existing`, and closed `fixed` finding (with its commit and evidence) without holding the merge. When `list` prints `[]`, as when the review ran on another machine, report "review dispositions unavailable locally" and rely on the `Reviewed:` line alone.

   Ask only about consequential missing requirements. A blocking mismatch stops before merging, or stops cleanup when the merge already happened. Fixes remain maintenance work on the existing branch while open; do not restart a lifecycle.

5. Squash merge, then confirm it landed. `gh pr merge <n> --squash --match-head-commit <head recorded in step 3>`, so a push after the checks above fails the merge instead of landing unchecked code. The subject is the pull request title, which is already Conventional; the body carries the resulting behavior and material assumptions from the pull request description rather than a list of the squashed commits. Omit `--delete-branch`: its post-merge local checkout fails on a repository whose default branch is checked out in another worktree, which reports an error after the merge has already succeeded and reads as a failed merge. Step 9 deletes the remote branch instead. Then re-read `gh pr view <n> --json state,mergedAt,mergeCommit`. Anything but `MERGED` stops here and is reported, including when the merge command exited non-zero for the reason above; check the state, do not assume either outcome.

6. Repair direct dependents from step 3 before deleting anything. Squash merging replaces the original commits, so dependents otherwise repeat absorbed work and risk unintended retargeting or closure.

   Fetch first and rebase onto `origin/<default>`; the local default branch lacks the squash until step 7.

   For each direct dependent: retarget it with `gh pr edit <n> --base <default branch>` while the old base still exists, so a failure surfaces here rather than after the deletion has already made it unrecoverable. Then drop the absorbed commits from its head with `git rebase --onto origin/<default> <boundary> <dependent head>`, where the boundary is the commit the dependent was built on. A dependent holding a merge commit (`git rev-list --merges origin/<default>..<dependent head>` prints anything) is reported, not rebased: a merge such as GitHub's "Update branch" can make the recorded tip an ancestor while the old commits still sit underneath. When the tip recorded in step 3 is an ancestor of the dependent (`git merge-base --is-ancestor`), that tip is the boundary. Otherwise the head was rewritten after the dependent branched, as when an earlier `/land` in a stack rebased it onto the default branch, and the dependent still sits on the head's old commits; the recorded tip would replay those absorbed commits onto the squash and conflict. Find them with `git cherry <recorded tip> <dependent head>`, which marks `-` each commit whose patch is already on the head; the boundary candidate is the last `-` line, and with none, report the dependent. The order of those lines proves nothing: a dependent's own commit that matches a head commit (a shared cherry-pick, an empty retrigger commit) is marked `-` too, and a boundary there silently drops the dependent's earlier commits. So, in either case, verify the boundary by content: everything the dependent holds up to it must already be on the default branch, which holds when `git merge-tree --write-tree origin/<default> <boundary>` prints `git rev-parse origin/<default>^{tree}` as its first line. Anything else means the boundary still carries the dependent's own work, or work the squash dropped; report the dependent instead of rebasing. Before pushing, confirm the dependent's own change survived: `git diff <boundary> <its headRefOid from step 3> | git patch-id --verbatim` must be non-empty and equal `git diff origin/<default> <rebased dependent> | git patch-id --verbatim`. An empty id is a failure, since two empty ids compare equal. A difference means a wrong boundary or new default-branch work beside the dependent's hunks; read the differing files, and report the dependent unless the default branch's new commits explain every difference. Run that branch's own local rungs, and push with `git push --force-with-lease=refs/heads/<dependent head>:<its headRefOid from step 3> origin <dependent head>`. The explicit lease fails if the dependent's owner pushed since step 3, even when a background fetch has moved the remote-tracking ref; report that dependent instead of retrying. Do the rebase in the dependent's own worktree where it has one, and never rebase a branch that is checked out somewhere else.

   Repair only direct dependents. A deeper chain keeps sitting on the old commits until its own base lands, and that run finds its boundary as above, so rebasing it now would only repeat work. A conflict that is more than mechanical stops here: leave the head branch undeleted, report which dependents were repaired and which were not, and treat the rest as `/address-review` work. Nothing below runs until every dependent is repaired or reported.

7. Verify the merge and default-branch health. Fetch and prune, locate `<default>`'s worktree with `git worktree list`, then run `git -C <that path> merge --ff-only origin/<default>`. Run the repository-required local checks on the updated default branch and report failures before cleanup. Pass `-C` so the right branch is updated, and use it in place of `git checkout <default>`, which fails when another worktree owns the branch.

   When recovery material exists, read `continuity` and preserve it before retirement. Record the confirmed merge and remaining cleanup in the retained copy of the task document outside a checkout slated for retirement; mirror if available. Keep the merged checkout clean of this bookkeeping, create no checkpoint merely to land, and leave legacy records as they are.

   Reaching this step straight from step 2, run step 4's conformance check here and resume at step 8 rather than step 5, because steps 5 and 6 belong to the run that does the merging. Someone else merged this pull request, so a blocking mismatch is reported rather than prevented, and the landing stops here.

8. Reconcile the tracker only for ticket-bound work. Where `setup-harness` installed the GitHub lifecycle workflow, confirm it already ran: the ticket closed, the parent closed once every child had merge evidence, and each unblocked sibling moved to mapped `ready_for_agent`. Where it did not run, or the tracker is not GitHub, apply those transitions by hand and say which ones you applied. Where the tracker is local markdown, read the `local-tracker` skill: the transitions are file edits that must be committed and pushed on the default branch, which step 7 has already fast-forwarded past the merge, and before step 9 retires the worktree. The explicit landing request covers these scoped reconciliation writes; name and verify their files and transitions without a repeated confirmation. Preserve unrelated default-branch work. A protected branch or transition outside that authority stops only dependent cleanup. A parent closes only when every child has merge evidence. For trackerless work, skip tracker transitions.

9. Once the merge is confirmed, by step 5 or the merged lane, delete the branch's review directory (its ledger and patches), which the merge made obsolete: `f="$(harness review path --branch <headRefName>)" && rm -rf -- "$(dirname -- "$f")"`. Then retire only this run's checkout, and only when clean. When it is a linked worktree, first list `git status --porcelain --ignored`: removal deletes ignored files too, so report each one, and refuse when any is local configuration or a secret (such as `.env*` or local settings) rather than regenerable build output, so the human can move it. Then remove it from the main checkout, the first entry of `git worktree list --porcelain` (`git -C <that path> worktree remove <this path>`), since a checkout cannot remove itself. When this run is in the main checkout itself, leave the checkout and its branch in place and report it. A squash merge leaves the local branch unmerged by ancestry, so delete it with `git -C <that path> branch -D <branch>` only after `git merge-tree --write-tree origin/<default> <branch>` prints `git rev-parse origin/<default>^{tree}` as its first line, which proves its content landed (POLICY's floor row on worktrees; only `land` and `abandon` retire a task worktree). Delete the remote head branch as well when this run did the merging, and only once step 6 reported every dependent repaired; an unrepaired dependent keeps it alive. If the checkout holds uncommitted changes or unpushed commits, refuse and report instead: this skill discards nothing, and `/abandon` is what discards unmerged work.

10. Report the pull request, whether this run merged it and the merge commit when it did, the requirements source, the review status (current, covered with later tests or docs, stale and accepted, required but never run and accepted, not required at level `off`, or none required), the remote branch deleted, the review ledger deleted, and the worktree removed. Where this run merged, report every dependent pull request that was retargeted and rebased, and every one that was left for a human. The merged lane skips steps 3 and 6, so it reports that dependents were neither enumerated nor repaired, which is not the same as reporting none. For ticket-bound work, also report the ticket and parent states, labels moved, and next ready frontier. For trackerless work, report that tracker reconciliation was skipped.
