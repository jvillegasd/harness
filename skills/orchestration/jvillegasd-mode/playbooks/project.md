# Project

**You own the roadmap.** Several features toward one product goal ("build an app that does X, Y, and Z") run as milestones. Each milestone is an epic built by `build`, and the whole project ships as stacked pull requests the human lands bottom-up, or that the run lands itself when the request says full.

1. **Frame.** State the product goal and the definition of done as pass/fail checks on the running product, one per capability the human named. In an existing repository, ground the scope with `code-search` through `delegation`. In a new one, choose the stack and layout as `agent` decisions, settling a fork a run can answer with `proto`.
2. **Write the roadmap** into the project's task document (`checkpoint`), committed on the first milestone's root branch so every branch stacked above it carries it; autopilot's grant line goes there too. It is the run's one task document, and each milestone's epic is its own document in `docs/agents/epics/`. The roadmap lists milestones in order, each a demoable increment that leaves the product working, with its own done check. The first milestone is the scaffold and the riskiest unknown: the product builds, its tests run, CI runs them, and the app can be driven the way `verification` will drive it (`principle-foundational-thinking`). Write each milestone's epic when you reach it, not up front, since what earlier milestones teach changes later ones.
3. **Hold the one gate.** Show the human the roadmap and wait for their go, because a project spends hours of model budget on a direction only they can confirm. Under autopilot, state it and start.
4. **Run each milestone.** Write its epic with `epic`'s steps, then build it with `build`'s steps. Its pull requests stack on the earlier milestone's pull requests they build on, as `build` shapes the stack from the blocker graph, and an independent one branches from the default branch. Verify the milestone's done check at the tip of its stack in the running product (`verification`), and add a `## Decisions` row. When the milestone changed what the roadmap assumed, rewrite the rest of the roadmap before the next one. In a full run, land the milestone's verified pull requests as jvillegasd-mode's Stack or full section describes before starting the next, so each milestone builds on the default branch.
5. **Deliver the project.** Check the whole definition of done at the tip. Hand over the stack bottom-up, each pull request with its readiness report and every `agent` decision in the root's description, so the human reads the project in one place and lands it with `/land merge stack <tip>`. In a full run, report what landed and what stopped at merge-ready.

Milestone tickets follow the tracker `docs/agents/harness.json` names, published only on the human's request, as `epic` describes.

**Reply:** the goal, the `agent` decisions first, the roadmap with each milestone's state and its pull requests, each pull request's readiness or merge, and what is still open.
